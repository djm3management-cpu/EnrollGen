# EnrollGen pilot fit: replacing Onyx, retaining SunFire and AgencyBloc

Audit date: 2026-11-12. Branch: `audit/onyx-replacement-pilot-fit`. Starting commit: `f64d831e2ef8bc055aa58aac36ec8b69453c19a0`; application baseline remains `85d51d99a41636b5a73054d4dd73d23e56fa0814`.

**EnrollGen is a plausible replacement for the inbound calling, scripting and recording portion of Onyx, but it is not a complete replacement today.** The largest functional gaps are general license/appointment routing, external DNC and consumer-local calling-hour enforcement, outbound transcription parity, manager supervision, a real manager permission tier, and AgencyBloc delivery. SunFire recording upload already exists; SunFire quote launch and AgencyBloc integration do not.

Keep AgencyBloc as the customer/policy system of record and SunFire as the quoting/enrollment system. EnrollGen should own call operations and their evidence. First verify whether the shop already uses AgencyBloc's native SunFire integration; building a second independent policy writer could create duplicates. AgencyBloc currently advertises SunFire connectivity and a quote/enroll workflow that returns beneficiary/policy data to AMS+. That is product-level evidence, not confirmation of this shop's entitlement or exact field behavior. [AgencyBloc Medicare integrations](https://www.agencybloc.com/agency-management-system/medicare-integrations/), [AgencyBloc FAQ](https://www.agencybloc.com/faqs/).

This audit changed only this report. No application execution, tests, migrations, provider-account access, production queries, deployments, imports or outbound deliveries were performed. Source and public vendor documentation were read; credential values are omitted. References are repository-relative at the application baseline. Existing `PILOT_READINESS.md` remains unchanged and its security/bootstrap findings remain prerequisites.

## 2. Feature findings and the work behind the estimates

### License and appointment routing

`carrier_rts` begins with carrier/channel/product-line, agent name/NPN/Clerk subject, status and **free-text** states/certification date (`029:3–17`). Migration 030 adds tenant/agent IDs, structured `state_appointments`, certifications, writing number, effective/termination dates and source-file hash (`030:3–13`), plus ingestion history. CSV/TSV/XLSX/XLS preview/normalization exists in `netlify/functions/_rtsIngestion.js:4–6,292–333`; commit has an admin check in `rts-ingest.js:340`.

This is not a licensing authority feed. `RTSTab.jsx:305–308` directly edits rows, and migration 033 deliberately allows agency-wide authenticated edits. Free-text status/states, inconsistent historical identity links and agent-editable readiness cannot become a safety gate without normalization and protected approval. `tenant_agents.licensed_states` is another roster field; it is not proof that routing applies it.

The Paragon matrix is separate: `vendor_agent_state_eligibility` uses source/plan-year/agent/state and six carrier booleans. Its comment explicitly says it never reads or syncs RTS. A row represents a license assertion, and missing noncritical carriers can still yield a **partial** eligible tier (`051:22–36,80–95`; `telephony/src/paragonEligibility.js:22–44`). This is vendor coverage selection, not “this caller's carrier appointment is valid.” Other inbound paths use generic claims, sticky preferences and direct DIDs; outbound claims the dialing agent without this general qualification check.

Proposed design, not implemented:

1. Normalize independently approved licenses and carrier appointments into a versioned eligibility snapshot keyed by immutable agent ID, state, carrier ID, product line and plan year, with effective/expiry/termination dates, certification state, source and approver. Do not infer an active license from an RTS label or a name match.
2. Resolve caller state from a trusted lead field or verified residence; area code/CallerState alone is not authoritative residence. Require carrier context for carrier-specific work. For unknown carrier, route only for permitted intake and recheck before carrier discussion/quote/transfer; if policy requires pre-route certainty, send to intake/overflow instead of guessing.
3. Apply the predicate **inside the atomic reservation** for initial routing, retries, sticky/direct callbacks, outbound and transfer targets. A UI filter or earlier ping check can go stale before the claim. Log policy version and rejection reason with safe identifiers.
4. Proposed deployment setting `ROUTING_ELIGIBILITY_MODE=off|shadow|enforce`: shadow compares without changing routes; enforce excludes unknown/stale/ineligible matches. Keep a separate protected operational stop. Turning the kill switch off must pause affected traffic or fall back to an explicitly approved fixed cohort—not silently route sales to anyone. `PARAGON_STATE_ROUTING_ENABLED` only controls the existing vendor path.
5. Test revoked/expired licenses, carrier aliases, plan-year rollover, stale snapshots, unknown state/carrier, no eligible agent, direct-DID bypass, transfer and 20 simultaneous arrivals. Preserve the existing reservation/idempotency mechanisms.

For a small inbound trial, a cheaper alternative is one verified state/product/carrier cohort where **every participating agent** has the required qualifications, with a server admission allowlist and defined overflow. That is deliberately narrower than general RTS-aware routing; it still needs approved evidence and fail-closed admission.

### DNC, outbound, screen pop and logging

Voice DNC is not merely cosmetic: `outbound_dnc_status` checks normalized phone/blind index within the tenant; both browser preflight and signed Twilio outbound execution check it, and failures stop dialing (`070:3–24`; `voiceOutbound.js:32–38,65–83`). SMS checks the selected contact's flag. No external federal/state scrub, refresh deadline, exemption evidence, consent ledger, consumer timezone check or application STOP/START synchronization was found. Twilio's own suppression does not automatically update the CRM boolean or AgencyBloc. Design one server policy decision shared by voice, SMS, campaigns, retries and conference dial-outs; no alternative dialing path should bypass it. The shop must supply its approved rules/provider and evidence requirements before implementation; agency business hours do not answer consumer-local restrictions.

Outbound recording is implemented, but transcription parity is not. Inbound TwiML starts both-track server streaming (`twilioVoice.js:77–82`); ordinary outbound TwiML only dials and records. The browser explicitly reserves server transcription for inbound or conference calls, leaving normal outbound on microphone/remote-audio capture (`InboundCallContext.jsx:108–110`). Remote-track failures are surfaced (`:852`), but browser dependency, closing/sleeping tabs and durable transcript recovery need separate outbound acceptance. Do not market that path as identical to inbound.

Screen pop currently means contact hydration and caller display, not automatically opening a full timeline. `InboundCallContext` reads contact metadata and audited `decrypt_pii` on ringing/active contact changes. `useContactDetail` separately loads activities, notes, follow-ups and policies. Join those under a protected call context, cancel stale requests on the next call, and preserve the active phone while opening history. AgencyBloc history is a separate integration; local current-plan fields are not a complete AMS policy history.

Call facts can save automatically. Business outcomes generally do not: `CallDispositionBox` requires a selected disposition and explicit save, except its short-call path. Its MA sale path requires completed intake. `NotesPad` also has a Save button. The session summary is largely generated from script/session state; the legacy batch transcription endpoint can produce a Deepgram summary, but neither establishes a reliable immediate AI summary for every call. Prefer suggested notes/outcome with agent confirmation and durable autosave, not an AI declaration that an application was submitted. Preserve failures/retries visibly and keep call completion independent of AMS availability.

### Manager functions, roles, SOA and languages

The dashboard has Today/This Week/This Month/30 Days and agency/individual selection. Metrics count calls, dispositions treated as sales, conversion and **average** duration (`dashboardMetrics.js:1–45`); enrollment pending verification is counted with enrolled. Queries refresh every 60 seconds (`useDashboardData.js:136`) and do not fetch direction for the primary call-record metric query (`:69–75`). This is not yet “answered inbound calls per agent / enrollments / close rate / total talk by day and week.” Define unique call versus leg, transfer attribution, answered versus offered, enrollment versus effectuated policy, multi-enrollment calls, denominator, timezone and week boundary before implementing a scoreboard. Move aggregation/permissions server-side; current frontend scope filtering is not authorization.

Presence and status history are useful foundations, but a live supervisor board needs a protected snapshot/feed including agent state, active call, elapsed time and freshness. A historical status log is not that board. Conference support includes participant operations, not listen-only/whisper monitoring. A supervisor feature must explicitly authorize the supervisor, separate what each participant hears, preserve customer recording integrity and log join/listen/whisper actions. Do not implement it by handing a manager an agent's ordinary call-control identity.

Current roles are inconsistent: legacy enrolled membership uses `agent`/`principal` (`000_session_tracking.sql:11`), tenant roster uses admin concepts, and evidence endpoints use verified Clerk admin claims. No uniform `manager` capability exists. A suitable pilot matrix is:

| Proposed role | Allowed scope | Excluded scope |
|---|---|---|
| Agent | Own active calls/evidence and assigned contacts; explicit shared queue access; own notes/disposition/intake | Role/license changes, arbitrary other-agent evidence, billing, secrets, bulk export |
| Manager | Defined team's live status, call metrics and reviewed evidence; approved reassignment/coaching | Credentials, billing, user-admin promotion, arbitrary deployment configuration |
| Admin | Provisioning, approved eligibility, destination settings and authorized agency-wide administration | No bypass of audit, tenant binding or secret-handling rules |

Implement capabilities server-side in JWT/membership resolution, API queries, RPCs, RLS and storage signing. Do not infer manager from a display label, use writable roster role as the security authority, or promote all supervisors to global Clerk admins. The permissive tenant predicate and legacy endpoints documented in `PILOT_READINESS.md` must be fixed before outside users access real data.

SOA has script steps, affirmative-response state, compliance detections/evidence and recorded audio; `call_records` also has `soa_on_file` and `soa_date`. No dedicated signed SOA object, product-specific document, signer evidence, immutable version, expiry/timing workflow or export/retrieval policy was established. Keep the shop's approved SunFire SOA process initially, store an authorized external reference and relevant capture metadata, and prove managers can retrieve it. Script wording and a passed detector are not themselves evidence that every scenario's SOA requirements have been met.

Legacy `transcribe.js` requests `detect_language=true` and returns a language, while live server/browser Nova-2 URLs omit language. Deepgram documents `en` as the language default and requires appropriate language/multilingual configuration for other speech. Spanish support in the provider does not establish support in EnrollGen's English scripts, regex matchers, coaching prompts or compliance rubric. Scope the first trial to English; enabling Spanish needs model compatibility, per-call language metadata, mixed-language and identifier tests, bilingual scripts/reviewer validation, and safe fallback. The legacy batch endpoint also needs ownership hardening before reuse. [Deepgram language configuration](https://developers.deepgram.com/docs/language).

## 3. SunFire integration

### Enrollment code capture and validation

The canonical intake field is **`sunfireCode`**, labeled “SunFire Confirmation Code.” It is distinct from `enrollCode` (Plan/Enrollment Code), `enrollmentId`, and `personalCode` (Sunfire/CRM). These must not be substituted for one another (`src/lib/enrollmentIntake.js:8–9`). Script notes can prefill it (`:46–50`), and existing call data can prefill it (`netlify/functions/enrollment-intakes.js:73`).

The React intake marks it required for UnitedHealthcare (`EnrollmentIntake.jsx:97`); the server normalizes and calls the same validation before `save_enrollment_intake` (`enrollment-intakes.js:51–59`). Validation is presence for UHC, trimming and the general 500-character field bound—not a provider-issued-code format, ownership or existence check. Database triggers also require a UHC confirmation for enrolled dispositions and a completed MA intake (`125_enrollment_intakes.sql:58–81`). Multiple intakes aggregate their codes onto `call_records.sunfire_code`; the queue uses the specific intake/enrollment key, not just the aggregate string.

Actual existence is evaluated asynchronously when the worker registers `sunfireEnrollmentCode` with SunFire (`ixUploads.js:61`). `ixClient.js:40–49` distinguishes invalid code/404 (`needs_attention`), duplicate/409 (`duplicate_on_sunfire`), retryable 429/5xx and terminal errors. Upload checkpoints and finalization receipts avoid treating a successful registration or PUT alone as completed delivery. A duplicate is a reconciliation condition, not proof that the correct recording was previously delivered.

The intake accepts only three hardcoded writing-agent names today (`enrollmentIntake.js:3,33`). Replace that allowlist and name-derived owner assignments with the pilot's protected IDs/roster before enrolling any pilot agent. Add a clear distinction among SunFire confirmation, carrier application/confirmation and eventual AMS policy number; a submitted application is not automatically an issued/effectuated policy.

### Quote launch with prefill

No current contact-bound SunFire launch action was found on the call screen. A plain agency portal bookmark is a small UI change and **does not prefill a quote**. Prefer the existing AMS+ → SunFire path initially if enabled for the shop; confirm which beneficiary fields and agent identity it carries and what comes back. The 2024 announcement alone is not proof of current entitlement. [AgencyBloc/SunFire announcement](https://www.agencybloc.com/about-us/agencybloc-sunfire-integration/).

For a direct launch, obtain SunFire's sanctioned partner launch/SSO API, test tenant, authorized agent/NPN mapping, beneficiary match/create rules, approved fields, short-lived launch-token format, redirect allowlist and completion callback contract. The server must authorize the active call/contact, send only permitted fields, record correlation IDs and issue a short-lived launch result. Do not put DOB/MBI/address or credentials into a query-string link, scrape the portal, or assume IX login grants quoting access. Reconcile the returned enrollment into the same intake/AMS policy, rather than creating a second individual.

## 4. AgencyBloc integration design — not implemented

### Existing GHL behavior

There are **two** relevant send paths. Both must be disabled or routed deliberately for an AgencyBloc shop.

**Current intake path:** `enrollment-intakes.js:59–61` validates/authorizes the call, saves via `save_enrollment_intake`, then attempts one delivery. The DB transaction stores intake fields, encrypts DOB/MBI/Medicaid number, updates follow-up/call code links and adds an encrypted payload snapshot to `ghl_enrollment_deliveries` with a monotonically assigned revision (`125:11–15`; current function in `132:28–49`). Non-test intake saves, including edits, create a delivery. This trigger is **intake save**, not necessarily a later enrolled disposition or carrier-confirmed enrollment. Avoid sending provisional data as an issued policy.

`integrations/enrollmentWebhook.js:3–19` returns without claiming when `GHL_ENROLLMENT_WEBHOOK_URL` is absent; queued work remains. It decrypts the snapshot only for delivery, rejects test intakes and POSTs JSON with `Idempotency-Key: job.id`. The Railway worker drains it (`integrations/worker.js:54`). Save success does not depend on provider success. Merely removing the URL pauses an accumulating queue; it is not a complete “nowhere” destination.

Exact intake payload field names (`enrollmentIntake.js:39`):

```text
planType, zip, firstName, lastName, dob, phone, email, state, mbi,
medicaid, medicaidNum, prevCarrier, newCarrier, planName, enrollCode,
premium, sunfireCode, effectiveDate, sixtyDayDate, sep, contractId,
planId, segmentId, enrollmentId, pcpName, agency, aor,
assignedUserId, assignedTo, hra, hraDate, submittedAt
```

The mapper overwrites agency with NGHS and uses hardcoded GHL user mappings/fallback. It omits a canonical contact/intake/call ID from the JSON body, compliance score, durable call page reference and `personalCode`. Sensitive values are intentionally delivered in cleartext over HTTPS after decryption; approve an AgencyBloc field allowlist instead of copying this whole GHL payload.

Claims use row locking/SKIP LOCKED, a 30-minute lease, five-attempt bound and revision ordering (`132:76–95`). A later revision waits while an earlier delivery is still retryable/in-flight; an exhausted earlier revision no longer blocks it. Completion schedules 60 × 2^(attempt−1) seconds (retries after 1, 2, 4 and 8 minutes before the fifth attempt; final failure is not claimed again), then marks terminal failure (`125:113–122`). The transport uses HTTPS, vetted/pinned public DNS, no redirects, 10-second request timeout and bounded responses (`integrations/transport.js:23–54`). Any 2xx is accepted as delivery success; there is no durable remote object receipt or verification that the CRM actually applied the record. Network ambiguity still requires destination idempotency. Failure text is generic, and the intake UI shows latest delivery status/attempt count (`EnrollmentIntake.jsx:79`). No complete contact-change stream or AgencyBloc reconciliation UI exists.

**Legacy post-call path:** `netlify/lib/postCallWork.js:475–533,657–690` maps similar beneficiary/enrollment fields, resolves tenant `ghl_webhook_url` and roster GHL user IDs, and sends on `outcome === enrolled` behind the pro-plan gate. It uses `claim_post_call_webhook`, records sent/error status on the call and does not share the intake queue/revision retry protocol. Do not assume the generic post-call worker's retries make this once-claimed external side effect reliably retryable. A separate configured hook can cause duplicate CRM delivery even when the newer intake destination is disabled.

### Proposed destination boundary

Use a small server-side adapter over a transactional outbox; do not generalize the entire telephony vendor layer. Proposed deployment setting `AMS_DESTINATION=none|gohighlevel|agencybloc` is **new**, not an existing env variable. Credentials, account IDs and endpoint allowlists remain server-only. Pin configuration/mapping version and destination account to every delivery so a configuration change cannot silently send old queued PHI to another account.

```text
authorized contact/intake/disposition transaction
  -> canonical event + revision + approved source snapshot
  -> destination policy (none / GHL / AgencyBloc)
  -> leased worker -> adapter -> receipt + external-ID map
                           -> retry / needs-attention / reconciled
```

1. **Canonical events:** `contact.created`, `contact.updated`, `contact.suppression_changed`, `enrollment.submitted`, `enrollment.corrected`, `call.completed`, `compliance.reviewed`. Treat intake draft/save separately from confirmed submission. Each event has deployment/tenant ID, immutable aggregate ID, revision, schema version, event ID, actor, event time and causation/correlation IDs. Keep original source snapshot encrypted; limit retention and log only IDs/results.
2. **Source of truth:** AgencyBloc owns the durable individual/policy lifecycle; SunFire owns quoting/submitted-enrollment confirmation; EnrollGen owns call facts, evidence and reviewed disposition. Obtain an explicit field-ownership matrix. If native SunFire→AMS creates policies, EnrollGen attaches call/compliance activity to the matching policy instead of independently creating it. No broad bidirectional sync in the first adapter.
3. **Adapter contract:** validate configuration; map approved fields; resolve/match individual; upsert authorized fields; resolve/link policy where authorized; append/update call activity; persist remote IDs/receipts; reconcile ambiguous results. Use a structured result (`delivered`, `retryable`, `needs_attention`, `suppressed`) with safe error codes. Provider-specific field names stay inside the adapter.
4. **External identity:** new protected mapping keyed by destination account + local entity type/ID, holding AgencyBloc individual/policy/agent/activity IDs and last applied revision. Match stable imported AgencyBloc IDs first. Phone is a lookup candidate, not unquestionable person identity: spouses can share phones, numbers can be reassigned, and multiple policies can belong to one person. Conflicting identities require review rather than automatic merge.
5. **Idempotency/order:** unique destination/account/event and aggregate/revision constraints; serialize events per individual/policy; checkpoint individual creation before policy/activity creation. If AgencyBloc lacks idempotency or upsert, use external correlation fields plus lookup/reconciliation and a local lock. After a timeout, reconcile before repeating a create. Never promise exactly-once remote writes without a provider contract.
6. **Retry/recovery:** retry timeouts/429/5xx with jitter and provider Retry-After; stop on invalid mapping/auth/permission errors until repaired. Bound attempts and age; dead-letter with owner notification; admin-only replay, actor audit and reconciliation. A call or intake save must not wait for AgencyBloc. Partial success must resume from the persisted step, not recreate the individual/policy.
7. **None mode:** no outbound PHI delivery or provider credential requirement. Preserve a minimal suppressed-event audit rather than accumulate live GHL work indefinitely. Re-enabling requires an explicit reviewed replay window; no surprise historical backfill. Disable the legacy GHL sender and related report side effects as well.
8. **Security:** authorized server event creation, scope-limited service credential where the vendor supports it, approved hosts, encrypted snapshots, no PHI in errors, audit of evidence access and sync/replay. Store a stable authenticated EnrollGen call-page reference in AMS; do not use a short-lived recording signed URL as a permanent call link or make recordings public. Any external evidence portal needs its own scoped authentication/access trail.
9. **Acceptance:** synthetic create/update, shared-phone collision, two policies for one person, multi-intake call, changed effective date/AOR, duplicate callback, timeout after remote commit, 429, revoked key, out-of-order revisions, test records, off/on replay, native-SunFire duplicate and suppression propagation. Reconcile counts and external IDs before real writes.

The existing GHL implementation can be wrapped behind this contract, but its hardcoded payload and old sender must be removed from the pilot execution path. Leave NGHS production untouched; keep compatibility and promotion to production as a separate project.
