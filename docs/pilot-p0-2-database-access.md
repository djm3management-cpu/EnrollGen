# P0-2: database access boundary

Unapplied, isolated-pilot changes on `pilot/release`. No push, deployment, live migration, hosted database connection, environment-file edit, dependency addition, stylesheet edit, or production operation was performed. `main` was never checked out or modified. The audit and P0-5 handoff govern this implementation.

## Membership and authority

A verified Clerk subject is a member only when `resolve_deployment_subject(subject, organization)` finds exactly one complete active binding: the singleton deployment profile and matching tenant organization, an active protected `enrolled_agents` row, the matching active service-managed roster row, and an active availability subject mapping with the same subject, slug, tenant and organization. A supplied signed organization must match; an absent active-organization claim can use the already protected deployment mapping. Empty, duplicate, inactive, removed, mismatched and unprovisioned identities fail closed. Recording access also requires the exact protected recording subject mapping.

`current_deployment_identity()` supplies the database caller's signed JWT subject/org to that resolver and requires the real database role to be `authenticated`. `is_current_tenant`, evidence, CRM, PII, follow-up and row policies all delegate to this model. Request headers cannot manufacture membership or enable a service-role path. Browser writes additionally have a statement guard, so unprovisioned callers cannot even submit a zero-row content PATCH successfully.

Authority comes from a protected enrolled `principal`, a service-managed `deployment_authorities` row, or verified signed Clerk admin/owner claims after membership resolution. A protected manager row contains an explicit array of approved enrolled-agent UUIDs; no label or roster field grants that scope. `tenant_agents.role` is never read as authority. Compatibility CRM records return a computed role from the protected source rather than the stored roster role. Provisioning payload roles still cannot create principals/admins, and migration 151 still preserves existing protected roles.

Ordinary agents read their own calls/evidence and assigned contacts, and write only approved content. No browser role, including an admin browser, can write roster, organization, tenant, subject, authority, ownership or assignment columns directly. Roster/operator provisioning remains service-only. Tenant, script, pipeline and contact-assignment administration goes through server handlers that resolve the caller again and construct tenant/actor fields themselves.

## New migrations

- `152_protected_deployment_identity.sql`: authoritative resolver, protected manager/admin mapping, replacement membership/CRM helpers, schema CREATE and default browser function revocations.
- `153_scoped_table_and_storage_access.sql`: replace all installed public-table policies, enable RLS everywhere, revoke table **and column** privileges, install explicit reference/read/content-update scopes, guard unprovisioned writes, secure views and storage.
- `154_scoped_browser_routines.sql`: protected PII/contact access, scoped CRM routines, reviewed EXECUTE allowlist, search invoker rights, pinned application/private helper paths and private-schema revocations. Unlisted routines remain service-only.
- `155_owned_workspace_writes.sql`: bounded content creation, deriving tenant and actor; the legacy default-pipeline browser RPC becomes a read, with configuration provisioned by an operator.
- `156_scoped_service_call_views.sql`: service-only call-log/entry/missing-recording views with protected owner UUIDs. APIs filter these in SQL before pagination. Ownership uses call/session/attempt/subject bindings, never the displayed agent name.

No historical migration was edited. Migration 153 drops **every** installed policy on every public base/partitioned table, including unknown bootstrap tables, then installs the explicit read/write allowlist. It does not rely on a second permissive policy narrowing an earlier permissive policy. Unrecognized public tables get RLS, no browser policy and no browser grant. The service role retains its intended table/function access; background/provider routines do not require an interactive Clerk identity.

Team review grants reads only; manager team access cannot write a peer's call disposition or follow-up queue. “Service” means server/operator use, after the handler's relevant membership/ownership/admin checks; it never means browser possession of the service key. ## Privilege revocations

- PUBLIC/anon/authenticated lose all public-table privileges and all prior column grants before explicit SELECT/content UPDATE grants are installed. No browser table-level UPDATE or INSERT/DELETE grant remains, and identity/role/tenant/organization/subject/owner/assignment columns have no column write grants.
- Tenants and roster reads have explicit safe projections; contact reads have the existing safe metadata/last-four projection. Plaintext names/phone/email/DOB/address, encrypted blobs and blind indexes cannot be selected directly from contacts. Assignment-scoped audited RPCs supply needed contact details.
- All browser access to `vendor_controls` and `vendor_control_audit` is revoked, including stale column grants. Both now have RLS. Their restricted pause/provisioning/reporting routines retain service access.
- PUBLIC and anon lose application function EXECUTE; authenticated gets only the commented allowlist. Service provisioning, settings/admin, vendor/telephony, crypto and job routines are excluded from that browser list.
- Browser schema CREATE, public sequence privileges, private key/rollback schema/table/function access, storage writes/column grants, and mutable-view grants are revoked. Current migration-owner default table/function privileges are closed for future objects; P0-4 must check other object owners' defaults too.

## Narrow scope decisions for owner review

1. No shared/unassigned contact queue was explicitly approved. Ordinary agents cannot browse or claim unassigned/peer contacts, their PII, notes, messages, intakes or opportunities. Administrators reassign through the server. Notes also require the author to be the caller, unless admin.
2. A manager requires an explicit service-managed team UUID list; an empty list grants no peer data. SQL team scope permits reviewed call/session/transcript/compliance evidence reads and does not confer contact PII, billing/configuration, provisioning or peer disposition writes. Existing service APIs retain their own-call scope for non-admins; a dedicated manager board/team API remains the separate PILOT_FIT supervisor work. No manager gets another agent's telephony/control identity.
3. Analytics/coaching aggregates without stable owner IDs and RTS ingestion logs are admin-only. Calibration/autoresearch rows without reliable tenant binding are service-only, even for admin browsers. Unbound/orphan evidence has no ordinary-agent read path.
4. RTS maintenance is own roster UUID or admin, replacing historical agency-wide peer edits. Raw vendor intel mutation and operational delivery/job/audit ledgers are service-only.
5. Shared scripts/knowledge and scoring taxonomy can be read by active deployment members, never unprovisioned signed-in users. Public CMS/geography/carrier/disaster/bulletin reference data is the explicit exception. CMS published-year filters are retained.
6. Browser direct recording storage access remains closed; short-lived authorized server capabilities remain the playback/download path. Message-media signing reads require a real message linked to an assigned contact. Both buckets are private.
7. Unreviewed views have no browser grant, even if a legacy/default grant existed. Only the five reviewed reporting views can retain authenticated reads; materialized and service views remain closed.
8. Default pipeline creation is an operator setup step, not a side effect of an ordinary browser read. Provision the default pipeline with the service-only pipeline RPC during P0-4 setup.
