### Presence, stale callbacks, and growth

Heartbeat interval is **15 seconds**; **45 seconds is the database lease**, not the ping interval. The server sweeps every 15 seconds, and routing tests lease expiry itself. Production `telephony_presence_policy.enforced=true`. Separate UUID phone sessions preserve multi-tab behavior; queued heartbeat/close updates prevent a late pong resurrecting a closed session. Reconnection does not force the manual availability toggle back on. Ownership checks protect a newer call from a stale release, child-leg evidence checks parent/attempt identity, and routing XML replay avoids repeat claims. These protections are covered by the existing tests.

Remaining failure modes: lost terminal callbacks can strand `active_call_sid`; a crashed replay request with NULL XML remains permanently “processing”; connected WebSocket authorization is not periodically rechecked; multi-replica transcript delivery is process-local (F22–F25). Production replay table: **43 rows, zero unfinished**, oldest September 11, roughly **90 KB** total relation size. There is **no TTL or cleanup job/index on age**. At 15–20 calls/day, initial routes alone add roughly 450–600 rows/month, with additional rows for reroutes and outbound; current size is small, growth is unbounded. Paragon reservations expire in 30 seconds and old reservation rows are deleted opportunistically by later pings after a day, which is a different lifecycle from routing-response cleanup.

**Agent identity is substantially tighter at token issuance than the older README claims:** verified Clerk subject/session selects an active server roster row, ignoring a supplied agent slug; agent socket token is signed and rechecked against active roster at connection, and Twilio callbacks require signature validation. It is not yet a complete authorization boundary: permissive roster RLS can undermine that trusted mapping; token lookup lacks tenant scope, connected sessions are not periodically revoked and the Media Stream is unsigned (F04/F08/F24/F29). Twilio voice token lasts one hour; agent WebSocket token's 15-minute expiry is checked on upgrade, not throughout an open socket.

### What the intent engine actually stores

The JavaScript catalog has **167 intents: 143 Medicare and 24 annuity** (`src/compliance/intents/index.js:27`). Production has **143 `compliance_intents` rows**, **one active MA v1 scoring template**, and **143 template items**; no annuity template is deployed. Classification filters direction but not product (F14).

1. Browser checkpoints/finalization store scrubbed `call_records.transcript_raw`/`transcript_diarized`, create/update `call_transcripts`, and maintain `call_records.transcript_id`, transcript `call_record_id`/`session_id`, checkpoint/final timestamps and tenant. Call records carry agent ID/name/NPN, contact, tenant, CallSid, start/end/duration and metadata. This is separate from encrypted CRM contact storage.
2. **Wrap-up**, not every detected live utterance or terminal Twilio event, invokes `score-call-background` with internal job secret and tenant/call ID. Subscription and seat gates can stop it. It loads the product's active scoring template.
3. `IntentClassifier` splits diarized text into **45-second windows with 15-second overlap**; PHI redaction happens before sending windows to the model. It detects direction from the first minute, defaulting inbound, and keeps the **highest-confidence result per intent**. This is not a log of every occurrence. `src/compliance/engine/IntentClassifier.js:12`, `:129`, `:197`.
4. `intent_detections` stores `call_id`, `intent_code`, detected/confidence/method/speaker, evidence text, window `segment_start_ms`/`segment_end_ms`, sequence/anti-pattern flags/details and LLM reasoning. `created_at` is the database insertion time; window offsets are relative to the call, not exact utterance timestamps. The insertion does not populate `intent_id` or a direct `agent_id`/`tenant_id`; those are joined through the call. `src/compliance/engine/ScorecardGenerator.js:121`; migration `supabase/migrations/001_compliance_engine.sql:106`.
5. `compliance_scorecards` stores call/template/thread/tenant, score/grade/points, pass/fail, auto-fail reasons, category/risk/sequence/sentiment/coaching/review data and created/updated times. `scorecard_items` stores per-question result/points/confidence/auto-fail/evidence timestamp and detection/template/intent linkage; `corrective_actions` carries call/agent/scorecard linkage and evidence. `src/compliance/engine/ScorecardGenerator.js:161`, `:224`, `:249`.

Under 120 seconds the engine creates an insufficient/N/A card with **no detections/items**. A 90–119 second Paragon billable call therefore does not get the full intent audit. Persistence is nontransactional, several returned SQL errors are ignored, and repeat jobs have no call-level uniqueness. **Main correctly rethrows classifier failures** instead of grading unavailable evidence, but background failure/gating has no durable retry or consistent terminal scoring status (F11–F15).
